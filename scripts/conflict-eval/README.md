# 冲突复现评估

用一组固定的虚构题目检查体检的语义扫描：四种发现（矛盾、漏记的变化、例外、依据已变）各报得准不准，没问题的题会不会被硬凑出问题。

## 运行

需要 `DEEPSEEK_API_KEY` 和网络。在仓库根目录：

```bash
DEEPSEEK_API_KEY=... bash scripts/conflict-eval/run.sh
```

脚本在临时的隔离目录里装上钉版宿主，用宿主的默认模型逐题调用现有的语义扫描，凭据只写进那个目录，退出时删除。逐题的原始响应和评分写到 `output/conflict-eval/`（已忽略，不进仓库），终端只打印汇总。GitHub 上的 `conflict evaluation` 工作流只能手动触发，跑同一个脚本。

不带 key 的部分在常规测试里：`tests/conflict-eval.spec.ts` 检查题目格式、覆盖面和评分规则。

## 题目与评分

题目在 `tests/fixtures/conflict-eval.ts`，每题有输入（记忆、指令文件片段）、期望的发现和一句期望结论。当前的扫描提示词不带记录时间，所以时间写在记忆正文里。

按题计数：命中率是 TP/(TP+FN)，误报率是 FP/(FP+TN)；把一类错报成另一类，既算前一类漏报，也算后一类误报。只认模型输出的类型，不按说明文字改判。模型调用失败记作失败、算漏报，脚本以非零码退出；分数低于阈值只在报告里标出。

阈值在 `thresholds.ts`，按改造后应该做到的水平写定：矛盾命中率不低于 90%，其余三类不低于 80%，各类误报率不超过 5%。题量小，实际上每类都要全对；这是明确案例的回归门槛，不代表真实使用中的比例。

评分只判类别。建议的内容对不对（比如该不该复查全局默认、给出的指令文件改动文本是否正确）要对照报告里的期望结论人工看。
